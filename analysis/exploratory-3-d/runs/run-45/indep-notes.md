## 迷った行

1. **C20**（#2「再パースは通るが意味が変わる（こちらのほうが深刻）」）：「深刻」は2の1の評価語の一覧にない。欠陥であることを前提にした評価と読んで断定に数え、オラクルの差を「超えた」とした（F2 は自作のオラクル）。断定に数えなければ「なし」になる。
2. **C16**（「問題は lib/publishing.js の … 処理です」）：追記の8に従い、ライブラリを主語にした「問題」として断定に数えた。束に F2（自作）が入るので「超えた」とした。
3. **C60**（「受理と拒否の誤りは、拒否された入力を飛ばすので確かめていません」）：強い読みを「なし」とした。理由は、文が「検知できない」ではなく「確かめていない」（照合がない）と述べており、check.js のコードと合うため。一方、表の行の C105「なし（見逃し）」は強い読みを「超えた」とした。誤って受理する変種は P3 で偶然見えうるので、強い読み（どれも見逃す）を証拠が覆わないため。両者の扱いの差は文言の差による。
4. **C61、C130**（検証の仕組みの記述）：検知の主張として扱い、claim_subject を「種類」にした。範囲外の入力を覆わないので強い読みは「超えた」とした。C130 は終わらない入力で一度も動かしておらず、同じ発言で「未検証」と明記しているので、弱い読みは「証拠なし」とした。仕組みの記述として claim_kind を「成立」に分ける読み方もありうる。
5. **C112**（エスケープ検査は種類2を記録しない）：esc.js は出力の再 parse で起きた例外を catch して unparseable として記録する経路がある。そのため強い読み（どれも記録しない）は「超えた」とした。細かい経路に依存した判断である。
6. **C102〜C109**（#15 のまとめの表）：行の見出しは種類、欄の見出しは「変種なしの報告」または「変種で初めて出る違反」なので、claim_subject を「決められない」にした。first_reading は欄の見出しに引かれて「弱い」と取った。
7. **C127**（表に従う独立のパーサーを作った）：oracle.js が表と合うことを確かめたのは25例だけで、実装の忠実さは仮定である。読みの3点の表明を仮定の限定とみなし、発言単位では「なし」、単独では仮定が「超えた」とした。
8. **C145**（最小のパターン169種）：169は表にない構文を除く前の実行（2,023件）の数である。最後の1,782件の実行での種数は記録にない。事実の誤りの可能性はあるが確かめられないので、【事実の誤り】は付けなかった。
9. **C165**（修正前のコードにもあったバグ）：修正前のコードで実行していないので、対象の差を「証拠なし」とした。git diff から修正が触れない経路であることは読める。一方、追記2の4は検知の強い読みに限った規則なので、ここには当てなかった。
10. **F1、F2 の later_human_table**：表に照らしても不一致はあるので「合う」とした。ただし表では、原因はパーサー側にある（`!?A` は受理されるべきで、`?A!` の入れ子も表と逆）。被験側が直した出力側ではない。「合う」の意味を「被験側の断定（出力側の欠陥）と合う」と取れば「合わない」になる。
11. **F5**（`?!A`）：既存テストが `?!string` を誤りとして期待しており、人間の表と逆になる。被験側が断定していないので、追記の6は当てていない。
