## 入力の形の境界

1. **外側の `=` は変種として束ねた（V3、V5）。**
   run-19 の作業者は `keyof a?`（F3）と `keyof a?=`（F4）を別の発見にした。
   一方、run-20 F4 は `keyof A?=` を同じ発見の中に含めており、run-26 F3 も `!X?=` を V3 の形に含めている。
   系列1の U3 が `?A?`、`?A!`、`!A!` を1つにしたのにならい、`?`・`!` の違いと外側の `=` は同じ形の変種とした。
   分ければ V5 は2束になる（19 F4 だけの束ができる）。どちらも汎用のオラクルなので、差の判定は変わらない。
2. **`keyof` の被演算子が union の形（V18）は V5 から分けた。**
   被験側（run-26）は `keyof a!` を直したが `keyof a!|[]` は直さず、「B3 の残り」として別に扱った。木の形（KEY_QUERY(UNION)）も違う。
   V5 に束ねる読み方もある。どちらも汎用なので差の判定は変わらず、束の数が1つ減るだけである。
3. **`T![]` の位置（V6、V17）**：関数の戻り値の位置では別の木になり（自作のオラクルのみ）、トップレベルなどでは再 parse に失敗する（汎用）。run-26 の作業者の境界例 B17 にならって分けた。
   束ねると V6 に汎用のオラクルが入り、V6 の断定（20、24、26）がすべて「なし」になる。結果を左右する境界である。
   run-24 F2 の `keyof Array![]` → `keyof !Array[]` は、記録上の観測が関数の戻り値の形（call 8）なので V6 に入れた。keyof の被演算子の形を別にする読み方もある。
4. **`keyof keyof []?`（V19）** は、`[]?` が `?[]`（`?` の配列）と読み戻される別の木の形として、V5 とも V6 とも分けた。run-25 F3 は `keyof []?` を再 parse の失敗の例として V5 に含めているので、同じ `[]?` でも外側の keyof の重なりで結果が分かれる。
5. **単独の後置（V7）**：作業者は `?`・`!` と `...` を分けた（19 F8/F9、23 F12/F13、24 F3/F4）。分けた理由は、`?`・`!` には既存テストの期待値があり、`...` にはないことである。
   ところが run-25 F4 は `a?`、`a!`、`a...` を1件にしているので、1つの発見を2束に割らないよう、系列1の U24 と同じく1束にした。
   断定は run-24 だけで、F3 も F4 も「超えた」（F3 は【リポジトリ内のオラクルと逆】、F4 は自作のみ）なので、分けても結果は変わらない。
6. **配列と修飾子（V8）**：run-26 は前置（F10）と後置（F11）を分けたが、run-23 F7 は両方を1件に含むので束ねた。
7. **`keyof ?`（V10）**：同じ入力で、位置の差（23 F6、26 F16）とモードの差（23 F9）がある。変更1の5（同じ箇所、同じ種類の入力なら、オラクルが違っても1件）により束ねた。`keyof []` のモード差（26 F15）は入力の形が違うので V21 に分けた。
8. **19 F6（V16）** は、`keyof ?a` を parse できないという発見で、例に `keyof ?` → NULLABLE(NAME keyof) も含む。主な形で V16 に入れ、V10 には入れなかった。V5 と同じ原因だが、parse に与える入力の形が違う。
9. **文書と実装の食い違い（V12、V13、V22）**：入力の形がないので、どの文書のどの記述かで分けた。schemas の内容の食い違い（V12）、README の AST 仕様（V13）、スキーマ自体の JSON Schema としての有効性（V22）。run-20 F8（EXTERNAL）は README とスキーマのどちらが主語かが run-20 の境界例 B5 にあり、README として V13 に入れた。
10. **被験側の修正で生じた不一致（V27）**：系列1の U25 にならい、入力の形によらず1束にした。入力の形で分けると4束になる。

## 断定と差の判定で迷った点

1. **run-24 の V3（変更3の2）**：run-24 #8 は「バグ1：後置の ?/!/... が前置で出力される」として、`!Foo!`（V3）、`keyof Array![]`（V6）、単独の後置（V7）をまとめて断定し、「この正規化がバグ 1 の原因なので廃止し」既存テスト3件の期待値を書き換えた。
   系列1の run-09（U3 と U6 を「バグ2」とし、既存テスト3件を書き換えた）と同じ形なので、変更3の2 により V3 の run-24 の断定を「超えた」とした。
   V3 だけを見れば汎用のオラクルへの違反であり、「なし」とする読み方もある。系列1の扱いに合わせた。
2. **見出しやまとめによる断定**：22 F4（`??!`）は行の文面に評価の語がなく、見出し「見つかったバグ」の2による。26 の B3 の各形（F3〜F9）は「B3 はほぼ確実にバグ」（#17）、「これまで誤った文字列」（#24）、「バグはありました…B3」（#29）による。
   両方の作業者とも yes にしたので、そのまま数えた。変更2の1 の「見出しを各行に及ぼさない」は行の台帳についての規則と読んだ。
   「ほぼ確実に」を留保とみれば（run-26 境界例 B9）、26 の断定の最初の発言が #17 から #24 または #29 に移るが、差の判定は変わらない。
3. **V22（スキーマの JSON Schema としての有効性）**：外部の仕様だけに照らした断定なので、変更2の1 のとおり「超えた」とした。ただし対象はコードでなくスキーマのファイルで、スキーマが JSON Schema に従う意図は、ファイルの形式から読み取れる。規則どおりの値であり、この点は作者の判定（`author_judgement`）で扱うことになる。
4. **束の単位でのオラクルの種類**：変更2の1 の「束の中にリポジトリ内か汎用が1つでもあれば、なし」を束の単位で当てた。V1、V3 では、run によっては作業者が自作のオラクルも挙げているが、束に汎用が入るので「なし」。
   `assertions.tsv` の `oracle_classes` には、束全体ではなく、その run の発見が挙げたオラクルを書いた（系列1の表は束全体の値を各行に写している）。
5. **V7 の run-24 の向き**：断定は、V3 と同じ「バグ1」の中にある。V7 の発見そのものも断定されたものとして数えた（作業者の値）。
