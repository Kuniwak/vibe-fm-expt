## 確かめられなかった点

- B3 の 3,144 は、check.js のコードと、ハーネス側の grep による推定である。再生していないので、行数として正しいかは確定していない。
- C27：別の AST に戻る入力で、publish の冪等性が成り立つかは分からない（被験側は調べていない。ハーネス側も再生しない）。
- C28：INNER_MEMBER / INSTANCE_MEMBER の引用付き名前、permissive 以外のモード、4種以外の文字で往復が成り立つかは、成果物から分からない。
- #19 で強めた traverse の検査（onLeave の親情報）は、既定の範囲（`npm run verify`）でだけ実行した。深い列挙（L=4 D=3）では回していない。発言はそれを主張していないので、台帳には差として入れていない。
- 回収した `home/` の verify/ はコミット後の最終版である（lint の修正と traverse の検査の強化を含む）。#15 の時点の check.js は記録（call 10 の Write と、その後の sed、Edit）からしか復元できない。差は lint の書式と traverse の onLeave の比較だけと読んだ。
- `.npmignore` によって schemas/ が npm に同梱されるか（C23）は、ファイルの読解だけによる。npm pack は誰も実行していない。

## 規則で決めきれなかった点と改善案

- 同じ発言の中で、見出しが断定し（「実バグ4件」）、別の節が条件をつける（「よければ…確定します」）場合（B2）。変更2の4（両論）はおもに範囲の限定を想定して書かれている。オラクルの条件づけにも両論を当てるかを明記するとよい。
- 「全反例」「全違反」のように、検査の結果の全体について述べた文で、帰属の手続きが一部の性質にしか及ばない場合（B1）。項目（オラクルか範囲か）と向き（成立側かその他か）の決め方を例示するとよい。
- 発言が成果物の文書（LEDGER.md）を「詳細は」と指している場合に、その文書だけにある不一致を発見に含めるか（B9）。
- 被験側のスクリプトの性質（Node のバージョンの互換など、C38・C45）を「その他」とするか、対象外とするか。
