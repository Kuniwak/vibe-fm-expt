## 主張

- **C7、C8、C17、C44（「バグ」をまとめた主張）**：#15 の表の行3に `??!` が含まれる。変更3の1で `??!` が別の木になることは別の発見（F4）とされ、F4 は RoundTrip と PublishFixed という自作のオラクルにしか照らしていないので、超えた（不一致側）とした。
  ただし、リポジトリのテストは後置を前置にする正規化を期待している（`goog.ui.Component?` → `?goog.ui.Component`）。この期待を `??!` に及ぼして「リポジトリ内のオラクルが逆の挙動を期待している」と読む余地もあるが、テストの例は単純な名前だけなので採らなかった。
- **C49（#20「バグ 1〜3 を修正し」）**：#20 の表ではバグ3を `!Foo?` だけで定義しているので、#20 の中で読んでなしとした。#15 の番号で読むと F4 が入り、超えたになる。C44（#16）は #16 の中でバグを定義していないため、#15 の番号で読んで超えたとした。2行の扱いが割れているのはこのためである。
- **C29（見出し「成り立つことを確認した性質 (回帰ガードとして固定済み)」）**：見出しの対象の差を、配下の C33 に引きずられて超えたとした。成立側の見出しに、まとめた主張の規則（1つでも超えたなら超えた）を当ててよいかは、規則に書かれていない。
  また、配下の「ビルド成果物」は run.sh に入っておらず、回帰ガードとして固定されていない。【事実の誤り】の候補として備考に書いた。
- **C33（エスケープ解除の順序非依存）**：Z3 の手書きモデルだけが証拠なので、対象は超えたとした。#15 の「Z3 … に使いました」が、対象をモデルに限る限定に当たるかで迷った。手法の名前を挙げただけで、モデル上の結果だとは述べていないと読んだ。
- **C31（「実コードでの全列挙で長さ 9 まで」）**：escape_enum.js の入力は4文字のアルファベットに限られる。この差を範囲の超過として数えるか、仮定（同値類の推論）の超過として数えるかで迷った。範囲だけに数えた。
- **C37（「黙って決まっている挙動です」）**：宣言されていないことを確かめた成果物がない。オラクルを証拠なしとしたが、超えた項目がないので向きは「—」にした。「その他」にするかで迷った。
- **C64（「入れ子側の解釈に揃えるのが自然です」）**：作者に尋ねずに、どちらが意図かを判断している。ただし評価の語で欠陥と断定してはいないので、なしとした。
- **C67（「常に」キーワードとして読む）**：証拠は grammar の変更そのもので、型名の位置では構造上つねに効く。`JsIdentifier` を使う他の規則には先読みがないので、範囲を超えたとする読みもありうる。
- **C74（「違反はすべて…衝突するケース」）**：検査が確かめたのは、違反した入力が `?[]` か `keyof` を含むことだけである。原因が方言の衝突かは確かめていないので、オラクルを超えたとした。細かすぎる読みかもしれない。
- **C75（「一貫して TypeScript の読み方」）**：call 64 は代表の15スケルトンしか表示していないので、範囲を超えたとした。「TypeScript の読み方」を、このパーサーの typescript モードとの一致として読んだ。TypeScript 言語の意味と読めば、対象かオラクルも超えたになる。
- **C36**：成立（AST は保存される）と不一致（ソース文字列は保存されない）が1文に入っている。入力が1行なので分けず、成立とした。
- **C2、C9、C11**：claim_kind を「不一致」とした。発見の報告に付随する文で、「その他」とする読みもありうる。
