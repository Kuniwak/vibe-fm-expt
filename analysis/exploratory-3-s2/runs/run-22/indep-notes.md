# run-22 独立の符号化：迷った行

主張は30行、発見は6行を符号化した。
迷った行は、主張の10行（C2、C6、C32、C36、C8、C23、C27、C38、C42、C47）と発見の1行（F4）。

## C2、C6、C32、C36（まとめた主張と見出し）

「バグが2件」「4件のバグ」の内訳のうち、バグ2は `?A?`、`?A!`、`??!` の3つの入力の形を含む。
変更3の1で入力の形ごとに分けると、`??!`（F4）は往復で同じ木になること（自作）だけに照らした発見になる。
そのため、まとめた主張は「超えた」（不一致側）とした。
被験側の区切り方（バグ2を1件とし、その中に `?A?` の再 parse の失敗という汎用の違反を含める）で束ねると、変更2の1の「束の中に汎用が1つでもあれば、なし」に当たる。
変更3の1を優先して読んだ。

## C8（P2 ✅ 違反なし）

#2 の検査範囲の段落にある「ランダム50万件、約250万回」は、call 8 の check3.js の件数である。
check3.js では NULLABLE と NOT_NULLABLE の publisher が差し替えられているので、その部分は実コードの publish を検査していない。
実コードでの P2 の検査は、call 3 の「トークン3個以下＋ランダム20万」である。
#2 の「回避策を検査スクリプトの中だけで当てて再実行」で開示されているとみて、対象は「なし」とした。

## C23（「保証できるのは、トークン3個以下の全入力と…」）

- 限界の表明だが、トークン3個以下の全入力について保証できると肯定的に述べている。そのため `claim_kind` は「限界」、`holds_claim` は yes とした。
- 範囲は【両論】とした。超える側は「トークン3個以下の全入力」、収める側は同じ発言の検査範囲の段落「40種類のトークン…最大3個」である。
- 参考：check.js は失敗を種類ごとに5件までしか記録しない。そのため、元のコードで失敗していた `keyof A ?`（3トークン）は call 3 の出力に現れなかった。また call 8 では、差し替えた publisher が後置を保つので、この失敗が隠れていた。この範囲で保証できるとした主張は、主張の時点の証拠そのものに反例を含んでいたことになる。ただし主張の時点で被験側がそれを見る手段はなかった。仮定の差として扱うか、備考にとどめるかで迷い、備考にとどめた。

ただし「those two bugs」は、F4 を含む2件をもう一度バグと呼んでいる。

## C38（「…意味の違う文字列になる」）

`??!` の AST の入れ子が逆転することを「意味が違う」と言い換えている。
評価の語の一覧（「バグ」「不具合」「欠陥」「誤り」「壊れている」）に入らないので、断定に数えず「なし」とした。

## C42（「前置に揃えると意味が変わる場合だけ後置形で出力」）

「意味が変わる場合」を、被験側は AST（meta を除く）の一致として運用している。
オラクルを「超えた」とする読み方もありうるが、同じ発言の「保証の範囲」で4つの性質に限定しているとみて、「なし」とした。

## C47（「前回と同じく、トークン3個以下の全入力とランダムな入力で4つの性質を確認」）

40語彙の限定は #2（別の発言）にしかないので、範囲は「超えた」とした。
オラクルも「超えた」とした。
「4つの性質」のうち P4 は、#2 で「1回ずつ訪問する」と定義されているのに、検査は訪問数とノード数の一致だけだからである（C10 と同じ）。
性質の定義が別の発言にあるので、迷った。

## 発見の F4

リポジトリ内のテストは、後置を前置に揃えることを期待している（`Object!` → `!Object`）。
これを、`??!` → `!??` の挙動を期待するリポジトリ内のオラクルとみなせば、【リポジトリ内のオラクルと逆】になる。
ただし既存のテストは入れ子の逆転までは期待していないので、そうはしなかった。
