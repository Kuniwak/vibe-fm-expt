## 確かめられなかった点

- lint と型チェックが通ったこと（C57、C62、C85）：被験側は npm test の出力を grep で絞っており、lint と tsc の出力そのものは記録にない。誤りの行が出ていないことと、テストが最後まで走ったこと（pretest の lint の後に mocha が走る）から読んだ。
- `keyof !?` の往復の失敗（F7）が、再 parse の失敗か別の木かは、test_roundtrip の出力から区別できない。
- 回収した /tmp/verify/check.js は最終版（call 39 で括弧の畳みを削除した後）。途中の版（call 4、5、17、22、23 の時点）は記録の中のコマンドから再構成した。
- 被覆（列挙が宣言した範囲を本当に覆っているか）は、被験側も確かめておらず、ハーネス側も確かめていない（成果物を実行しない方針）。
- C64、C69 で挙げた `keyof ??` の形の AST が、修正前の文法から parse で得られるかは確かめていない（再生しない方針）。
- F9（接尾辞の `...`）に対応するリポジトリ内のテストの期待値がないことは、元のコミットの tests/test_publishing.js だけで確かめた。tests/test_parsing.js ほかは見ていない。

## 規則で決めきれなかった点と改善案

- 評価の語の一覧（変更2の1）に「問題」「issue」「曖昧さ」「副作用」「直す」が入るかが決まっていない。一覧を閉じた形にするか、「問題」の扱いを明記するとよい。
- 汎用のオラクル「出力器の出力を同じパーサーで再び parse できる」の違反が、パーサー側の受理の不足（F6）として報告された場合に、その発見のオラクルを汎用とみなすかが決まっていない。出力器側の発見（F3）と同じ束にするか、別の発見とするかも、変更3の1（入力の形で分ける）だけでは決めにくい。
- 「全 fixture」のような範囲の言い回しの誤りを、範囲の超過とするか【事実の誤り】とするかの線引き。
- 被験側が途中で性質（norm）を変えた後に「前回定義した性質」と述べた場合の扱い（C54）。
