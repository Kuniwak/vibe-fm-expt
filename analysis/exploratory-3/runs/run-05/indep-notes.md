## 迷った行

### C6（両論か、なしか）
「そこを完全に証明しました」の「完全に」を、対象（実際の publish/parse の組）について証拠を超える内容の明示と読んだ。
収める側は、#4 第1段落「Lean が検証するのは Lean で書いたモデルの性質で…対象外です」と、「検証できていない範囲」の節の「この部分は証明ではなくテストで裏付けています」。
「完全に」を、sorry を使っていないという証明の完全さとだけ読めば、対象は明示されておらず、変更2の4の第3項により「なし」（単独で超えた）になる。

### C7a（事実の誤りか）
文法ファイルの中で unescape を書いている規則は4つ（MemberName、FilePathExpr、StringLiteralExpr、RecordTypeExprEntryKey。各2引用符で8か所）である。
モジュールパスは FilePathExpr、external は MemberName を経由する。
「文法ファイルの5か所」は利用する文脈の数え方であり、Lean ファイル冒頭の注記も4つの規則名を挙げて「5か所」と書いている。
件数の取り違えとまでは言えないと判断し、【事実の誤り】をつけなかった。

### C12（オラクルの両論）
「1文字ずつ正しく解釈した場合」の「正しく」は、被験側が自分で定義した decode（\c をそのまま残すなど）に照らしたものである。
同じ箇条書きの次の文「置換の順番…のせいで誤って解釈されることはない、という意味です」が、主張を2段の置換と1段の解釈の一致に収めている。
入力の quote には両方の文が含まれるので、行全体を一体として読めば「なし」にもなりうる。

### C16 と C17（同じ quote の割り振り）
入力の2行は quote が同一である。
C16 を往復と範囲（174,762通り）の部分、C17 を「定理3の内容をチェック」の部分として符号化した。
元の作業者が別の割り振り（たとえば範囲の主張と結果の主張）をしていれば、突き合わせは行の対応から確かめ直す必要がある。

### C17（対象の超過）
定理3のチェックは、テスト内に書き写した regex 連鎖（unesc）と JS で書き直した decode の比較であり、生成されたパーサも Lean のモデルも実行していない。
節見出し「モデルと実際のコードの一致の確認」と同じ文の「実際の」から、実コードについて述べたと読んで「超えた」とした。
regex は文法アクションと字面上同一なので、実質の差は小さい。

### C20（オラクル）
差分テストは、モデルの escape と addQuotesForName の出力を直接比べていない。確かめているのは、実コードが定理1の性質を満たすことと、書き写しの unesc が decode と一致することである。
「対応をテストで裏付け」を「モデルと JS が同じ関数であることの確認」と読めばオラクルで超えている。
「証明した性質が JS でも成り立つことの裏付け」と読んで「なし」とした。

### C22b（向き）
差の値は4項目とも「証拠なし」とした。
向きの語彙には「証拠なし」に対応する値がないため、証拠のない成立の主張として「成立側」とした。「と判断しています」という留保がついている。
