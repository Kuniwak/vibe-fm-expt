# run 間と作業者への情報の漏れを防いだ方法と、その実績

別の実験の参考として、この実験で情報の漏れを防ぐために取った方法と、実際にどうだったかをまとめる。
漏れには2つの経路がある。
1つは run と run のあいだ（被験側の AI に、前の run や実験の情報が届くこと）で、もう1つは分析の作業者（サブエージェント）に、仮説や正解や結果が届くことである。

## 1. run と run のあいだ

### 方法

- **run ごとに新しいコンテナを使う。**
  `docker run` にボリュームのマウントはない（`scripts/common.sh` の `agent_run_opts`）。
  run の後、`docker cp` でホームと `/tmp` を回収してから、コンテナを `docker rm -f` で消す（`scripts/collect.sh`）。
  被験側が書いたファイル（メモリ、`/tmp` の検査スクリプトなど）は、そのコンテナと一緒に消える。
- **イメージに実験の情報を入れない。**
  イメージのビルドに使うのは `image/` だけで、仮説、事前登録、結果、記録は含まれない。
  認証のトークンはイメージに入れず、実行時に環境変数で渡す。
- **各 run の直前に probe を走らせる。**
  run と同じイメージ、ユーザー、環境変数、ネットワーク、Claude Code の起動オプションで使い捨てのコンテナを起動し、`/context` で被験側に読み込まれるもの（指示ファイル、メモリ、MCP サーバー、スキル、プラグイン）を一覧する（`scripts/probe.sh`）。
  基準（`probe/baseline.json`）にないものが1つでもあれば、非ゼロで終わる。
- **最初の発言のファイルを sha256 で照合する。**
  登録済みの値と一致しなければ、run を起動しない（`config/conditions.tsv`）。
- **ネットワークを許可リストに絞る。**
  既定では、許可したドメインへの HTTPS だけを通す（`config/allow-domains.txt`）。適用したルールは run ごとに `record/network.log` に残る。
- **判定役（人間の代わりに返事をするプログラム）も、別の使い捨てコンテナで動かす。**
  判定役は、被験側の発言を受け取って「お任せします」か決まった発言かを選ぶだけの、盲検の判定役である（事前登録3章）。
- **ハーネス側から被験側への情報も絞る。**
  系列2で対象リポジトリのビルドを直したとき、修正のコミットやメッセージが被験側に見えないよう、元のコミットを作り直す形で入れた（事前登録12.2）。

### 実績

- `runs/` に probe の記録が残っている46回の run で、結果はすべて `RESULT: OK (only product defaults; matches baseline)` だった。
- 系列2の run-26 で、被験側が作業中に自分のメモリへ書き込んだ（利用者が判断を任せるという好みなど）。
  このメモリはコンテナの中にだけあり、コンテナと一緒に消えた。
  次の run の probe でも、メモリは検出されていない。
- probe の結果に `config_top: in baseline but absent now: ['cache']` という注記が出た run がある（run-18、run-19 など）。
  結果は OK で、基準にあったものが無いという注記である。意味は確かめていない。

## 2. 分析の作業者（サブエージェント）へ

### 方法

- **指示を、作業者が記録を読む前に固定してコミットする。**
  コミットの時刻が、結果を見て指示を変えていないことの証拠になる。
- **作業者に読んでよいファイルを指示で列挙し、それ以外（事前登録、正解、独立な確認の結果、ほかの run、記事の草稿）は読まないよう指示する。**
- **分析者が知っていることは、作業者への指示に入れない。**
  規則の文書には分析者の事前の知識を書くが、作業者には、その部分を除いた指示だけを渡した（`analysis/exploratory-4-tried/brief-table1.md`）。
- **見せる材料を機械的に加工する。**
  「AI が実際に試したこと」を書く作業者には、記録から AI の文章、思考、人への質問を除き、道具の入力と出力だけを抜き出したものを渡した（`scripts/analysis/tool_calls.py`）。
- **同じ作業を2人に独立にさせ、互いの結果を見せない。**
  食い違いはどちらにも寄せずに並べる。

### 実績と、弱いところ

- 読んでよいファイルの制限は、指示で求めただけで、仕組みで強制してはいない。
  作業者が実際に何を読んだかは、作業者自身の報告に頼っている。
  報告では、どの作業者も指示の範囲だけを読んだと述べていた。
- 作業者には、ファイルを書くことがハーネスの規則で禁じられていた。
  そのため、作業者は本文を返答に含め、分析者がそれを機械的に取り出して保存した。
  作業者が自分でファイルを書き換える経路は、結果としてなかった。
- 作業者の1人が、回収したリポジトリの写しの中で `git status` を実行した（run-24）。
  `.git/index` の時刻の情報が更新された可能性がある。ファイルの中身は変わっていない。
  以後の指示では、作業ツリーと index を変える git のコマンドを禁止した。
- AI の発言を除いた材料にも、AI が書いたスクリプトのコメントや、AI が書いた README と台帳の中身は残る。
  そこで、これらを判定の中身の根拠にしないよう、規則で定めた。
- 分析者（ハーネス側のセッション）は、すべての結果を見ている。
  分析者の読みが入る箇所（要約、比較表）は、そう断ったうえで生データへのリンクを付けた。

## 3. 別の実験に持ち込むときの要点

- コンテナを使い捨てにし、ボリュームを共有しなければ、run 間の漏れの経路は、イメージ、ネットワーク、認証の3つに絞れる。
- 被験側に読み込まれるものを、毎回の run の直前に、run と同じ条件で一覧して基準と比べる（probe）。
  漏れがないことを、記録として残せる。
- 作業者への制限は、指示だけでは強制できない。
  強く制限したいなら、作業者に渡す材料を別のディレクトリに写し、そこだけを読める環境で動かすほうが確かである。
  この実験では、そこまではしていない。
