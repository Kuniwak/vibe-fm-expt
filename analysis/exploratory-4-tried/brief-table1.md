# 表1の作業者への指示

担当の run で、AI が実際に試したこと（検査の実行）を表にする。
AI の発言は使わない。
道具の入力と、実行した環境が返した出力だけから書く。
規則は `rules.md` の「表1」の節と同じで、それを写したものである（`rules.md` そのものは読まない）。

## 読んでよいもの

- 担当の run の `analysis/tool-calls.md`（記録から、AI の文章、思考、人への質問を除き、道具の入力と出力だけを並べたもの）。
- 担当の run の `home/` の下のファイル（run の最後の状態）。
- 対象リポジトリの git の履歴（`git log`、`git show`）。作業ツリーと index を変えるコマンド（`git status`、`git checkout`、`git stash` など）は使わない。

ほかのファイル（`analysis/` のほかのファイル、`record/`、`preregistration.md`、`confirm/`、`reference/`、ほかの run、このディレクトリのほかのファイル）は読まない。

## 表1：実際に試したこと

1行を、検査を1回実行したことに当てる。
「検査」は、ライブラリかモデルの振る舞いを判定するか、出力を見るために実行したものとする。
例：検査スクリプト、既存のテスト（`npm test`）、証明の検査（`lake build`、`lean`）、ソルバー、TLC、入力を手で与えて出力を見る `node -e`。
ファイルを読むだけのもの（`cat`、`grep`、`ls`）、ビルドだけのもの、git の操作は行にしない。

| 列 | 書くこと |
|---|---|
| 番号 | `tool-calls.md` の T 番号 |
| 時刻 | その呼び出しの時刻 |
| 種類 | 全列挙、ランダム、既存テスト、証明の検査、ソルバー、手で試した入力、その他 |
| 対象 | 実コード、モデル、両方。実コードなら版（元のまま、または、どの T 番号の編集までを含むか） |
| 判定している条件 | 検査が違反や失敗とみなす条件を、コードからそのまま引用する。手で試した入力なら「なし（出力を見ただけ）」 |
| 入力の範囲 | 生成の仕方、語彙、長さや深さの上限、件数、モード、開始規則。コードと出力から分かる範囲で書く |
| 比較の緩め方 | 比べる前に除いたり同一視したりしたもの（`meta` を除く、など）。コードの引用を付ける。なければ「なし」 |
| 記録された結果 | 出力に出た件数、違反、反例を引用する |
| 備考 | 背景で実行したもの、出力が途中で切れているもの、確かめられなかったこと |

次の規則に従う。

- 判定している条件と入力の範囲は、コードと出力から書く。
  コメントや変数名、出力の見出しの言葉は、判定の中身の根拠にしない。
  AI が書いた文書のファイル（README、台帳など）も根拠にしない。これらは AI の主張であり、`tool-calls.md` の `Write` の入力に現れても、実際の側には使わない。
  コードと出力が食い違うときは、コードを優先し、備考に書く。
- 同じスクリプトが途中で書き換えられた場合は、その行の実行の時点の版を使う。
  版は、それより前の `Write` と `Edit` と `sed` などの呼び出しから組み立てる。
  組み立てられないときは「確かめていない」と書く。
- 評価の語（十分、不十分、緩い、など）を使わない。
- 表のあとに、スクリプトごとの一覧（名前、書いた T 番号、書き換えた T 番号）を付ける。
