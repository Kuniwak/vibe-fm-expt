## 判定の道具の限界（s2-d と s2-y の両方に当たる）

次の2点は、もとの道具では、表の判定と実際の出力が合わなかった。
1は規則が見ていないものであり、規則を後から変えると結果を左右するので、直していない。
2は道具の不具合として直した（実験者の判断、2026-11-19）。

1. `orig` の基準がすでにテストに失敗している場合（exit 1 -> 1）、変種で失敗の件数が増えても、新しい失敗の行が既存の種類（数字を除いた行）に収まれば「非検知」になる。
   該当する「非検知」のすべてで、失敗の件数は増えていた。
   - s2-d：run-27 S1 M2（1 -> 3）、M3（1 -> 2）、run-28 S1 M3（7 -> 8）、run-29 S1 M2（14 -> 16）、M3（14 -> 15）、run-32 S3-timeout M2（9 -> 11）、M3（9 -> 10）
   - s2-y：run-39 S1 M2（7 -> 9）、run-44 S1 M2（2 -> 4）、M3（2 -> 3）、run-45 S1 M3（10 -> 11）
   - `orig` の基準が失敗するのは、被験側が足したテストが被験側のライブラリの修正を前提にしているためである。
2. run-45 S3 の `orig` M3 は、もとの道具では「検知」だった。
   出力の先頭の JSON（違反の種類ごとの件数）でキーの順序が入れ替わり、行末のカンマの有無が変わったことだけによる。違反の件数も違反の行も基準と同じである。
   `summarize.py` が種類を作るときに行末のカンマを除くように直し（テストは `confirm/test_summarize.py`）、系列2の条件D、D2 のすべての写し（run-27〜32、39〜45）の判定を作り直した。
   判定が変わったのは run-45 S3 の `orig` M3（検知 -> 非検知）だけである。ほかは「新しい違反の種類」の列の表示（カンマの有無と、同じ種類の重複）だけが変わった。s2-d の `tables.md` は変わらない。
   JSON の行を新しい種類として拾った run-45 S3 の M1、M2 の「検知」は、基準にない種類（`P2-publish-throws`、`P5-traverse-throws`）が新しく現れたもので、直した後も「検知」である。

   規則が見ていないものであり、1と同じ理由で直していない。

   - s2-d：run-32 S3-timeout の `orig` M2
