## 迷った点

1. **S1 に npm test と往復性の node -e を含めたこと。**
   S1 の時点で報告が検証として述べたのは、主に `lean verification/Jsdoctypeparser.lean`。
   ただし #5 は「補強として」40,000 件の往復性の確認と `npm test` を挙げ、#11 の Test plan も `npm test` と `lean` を並べている。

   往復性の node -e は call 20 のインラインのコマンドで、ファイルとしては残っていない。原文をレシピに写した。乱数の種は固定されていない。
2. **S3 に newv.js の比較を加えたこと。**
   run.sh は変種なしでも exit 1 になる（種類1の違反 43,080 件）。そのため、終了コードでは判定できない。
   summary の例示は各グループの短い5件だけなので、新しい違反が例示に出ないこともある。
   被験側は段階4で、変種ごとに `node /tmp/mut/newv.js /tmp/mut/base.jsonl /tmp/mut/vN.jsonl` を使い、ベースラインにない違反を見ていた（call 69〜71）。#31 でも「ベースラインとの差分で見つけられます」と述べている。

3. **S3 の out/ の古い結果。**
   写しの verification/out/ には、変種3の結果が残っている。変種3はエスケープのループで、種類3が5件出る。
   run.sh が途中で失敗すると、newv.js が古い結果を読み、偽の「新しい違反」を出す。これを防ぐため、レシピの最初に out/ の結果のファイルを消すことにした。
4. **S3 の inputs に S1 の入力を残したこと。**
   `(x:) => string` などは修正前のライブラリでの違反で、被験側は修正済みと述べている。
   #16 では `(x:) => string` を種類2の違反として挙げたうえで、修正後のコードについては「誤検知」と述べた。
   「記録の最後までに違反として挙げた入力」には当たると判断して残し、note にこの経緯を書いた。
   `(a: number, b:) => void` と `(...x:) => y` は種類を述べていないので、kind は `—` とした。
