## 迷った点

1. **S1 の引数。** README と call 72（段階3の最初に被験側がそのまま実行したもの。この時点で verification/ は S1 から変わっていない）は既定値（`rt-diff-test.js` は seed 1・200000件、`fuzz-roundtrip.js 1 100000`）を使っている。一方、段階1の最後の実行（call 67）は `rt-diff-test.js 3` と `fuzz-roundtrip.js 21 100000` だった。#25 は README を再実行の方法として案内しているので、README の引数を採った。
2. **S1 の `&&` 連結。** call 67 は `&&` でつないでいるが、レシピではすべての手順を実行するようにした。どの node スクリプトも S1 では違反があっても終了コード 0 を返すので、検知はもっぱら出力の行に頼る。
3. **npm test を含めた。** S1 では、#25 が「モデルと実際のコードの照合」の中で既存テスト（回帰テスト11件を追加して全346件）を挙げている。S3 では、#47 が「既存の 346 テストと lint は通っています」と書き、#50 が回帰テストに触れている。ハーネス側が「被験側の検証」を verification/ に絞る場合は、npm test の行を外せばよい。
4. **S3 の基準状態はもとから FAIL。** `run-all.sh` は、変種がなくても precedence.js の違反11,251件で終了コード 1 になる。そのため、終了コードによる検知（0→非0）は起こりえない。precedence.js の出力に出るのは最短の40パターンだけで、件数の行は数字を除くと基準の出力と同じ形になる。このため、新しい違反パターンが41番目以降にしか現れない種類1の変種は、比較で非検知になりうる。被験側自身は `--save` の JSON を基準の JSON と比べて判定していた（`/tmp/mutants2.sh` と `/tmp/newviol.js`、call 111〜112）。これは被験側の変種手順の一部なので、レシピには含めなかった。ハーネス側が被験側と同じ判定のしかたを再現したい場合は、`node verification/precedence.js 1 60000 --save F` と `node verification/robustness.js --save F` を基準の状態と変種の状態で実行し、`/tmp/newviol.js BASE MUT prec|rob` で比べればよい（写しの /tmp にある）。
5. **時間制限。** S1 のスクリプトには時間制限がない。終わらない変種を当てるとスクリプトが止まり、入力も示されない（#28）。全体の5400秒を食いつぶさないよう、各手順を `timeout 600`（npm test は 900）で包んだ。これはハーネス側による追加である。S3 は被験側の `LIMIT=300` をそのまま使った（最悪で約30分）。
6. **VIOLATION_RE の `--> FAIL`。** この行は手順の名前を含まない。基準の状態の precedence の FAIL と区別できないので入れず、`--> TIMEOUT` だけを入れた。

## 入力の抜き出し

- 抜き出しの範囲は次のとおり。
  - S1：段階1の発言（#1〜#25）と、被験側の検査や手作業での確認の出力（call 16〜31）。
  - S3：S1 の分に加えて、変種を当てない状態の違反として #28、#47、#49、#50 が挙げたもの。#28 の手作業の照合（call 73）も含む。さらに、最終の run-all の出力 `/tmp/runall-final.txt`（写しの S3/tmp にある）に並ぶ40パターンのうち、発言にないもの。
- precedence.js が報告した違反11,251件（`/tmp/final-prec.json`）と、call 128 の系統別の一覧（5,117系統）は、全部は写していない。被験側が発言で具体的に示したものと、run-all の出力に出たものに限った。
- 含めなかったもの：
  - `1!`、`A...`、`function(A...)`、`[A, B...]`（call 21・22 の「AST differs」や「false」）。接尾辞を接頭辞にそろえる出力が往復で別の AST になる例で、被験側はいったん意図した正規化とみなした（call 24）。そのあと方針を変えて出力を変えたが（#10〜#11、#25「既存の出力が変わります」）、#25 の表にはバグとして挙げていない。
  - `A.'a\b'` と `A.'a\\b'`（#5「バグとは判断していません」）。
  - 変種でだけ出た違反（`?A|A`、`A!=`、`A.<1, *>`、`(a:) => X`、`external:A`、`A."d\"q"`、`A[]` の traverse、`typeof A`、`*!=` など）。
- kind について：段階1の入力は、段階2より前で分類がないので `—` にした。例外である `(a:) => void` などは定義上は種類2にあたるが、被験側は #28 で「前回直したクラッシュ」と述べただけで、入力を挙げて分類してはいない。そのため `—` のままにした。ただし `A![]` と `?A[]` は、#28 で種類1の表に再掲されているので、S3 では `1` にした。
- 段階1の入力の多く（`typeof A.b`、`(a:) => void`、`!A!`、`keyof A!`、`??!` など）は、被験側の修正後のライブラリではもう起きない（修正済み）。それでも、被験側が違反として挙げたものなので含めた。
