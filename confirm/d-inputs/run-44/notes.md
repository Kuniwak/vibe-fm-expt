## 迷った点

1. `npm run verify` をそのまま使うか。package.json の verify は `&&` でつないでいる。ところが precedence.js と robustness.js は基準の状態でも終了コード1を返す（5,297 件、19 件の違反）。そのため、そのまま使うと robustness.js と lean まで進まない。被験側は `npm run verify` を一度も実行しておらず、実際の検証は runall2.sh で各検査を個別に回していた。そこで個別実行を選んだ。
2. 終了コード。S1 は基準ですべて 0 なので、どれかが非0なら非0を返すようにした。S3 は基準ですでに1になるため、終了コードは判定に使えない。VIOLATION_RE で判定する。
3. 制限時間。S1 の時点の被験側は制限時間を付けずに実行していた。同じ検査（往復とテスト）に段階3で被験側自身が付けた `timeout 300` を S1 にも付けた。S3 の制限時間は runall2.sh のもの（300/300/300/600/900）。制限時間で止まったときは `@@ <step> timed out` を出す。ただし VIOLATION_RE には入れていない。被験側は V2・V3 が止まることを「△（違反の報告にはならない）」と評価していた（#15、#39）。
4. S1 の fx.js は publish の例外を捕まえないので、異常終了しても入力を示さない（被験側の評価は「△」、#15）。この場合も S1 の終了コードは非0になり、summarize.py の規則では「検知」に数えられる。被験側の評価と食い違う可能性がある。
5. S1 の `npm test` は lint（eslint .）、build、nyc（check-coverage 100%）、tsc を含む。カバレッジが 100% を下回ったり lint に違反したりしても失敗する（`ERROR:`）。これはバグの検知ではない。run-14 にならって VIOLATION_RE に `ERROR:` を入れた。
6. V1（Lean）は JS を読まない。参照変種には反応しないはずだが、報告で検証として述べているので含めた。
7. S3 の V4・V5 は、違反の例を種類ごとに先頭の数件（V4 は8件、V5 は3件）しか表示しない。このため変種によって基準の違反の並びが変わると、基準にもあった違反が例の行に「新しく」現れることがある。V5 は文法ファイル `peg_src` から入力を生成するので、文法を変える変種では入力そのものが変わる。さらに、3000 ms の壁時計で止まったと判定するので、コンテナが遅いと止まっていない呼び出しも「hang」と報告されうる。いずれもレシピのヘッダーに書いた。
