## どの報告を「最後の報告」としたか

固定発言（U10）の直前の発言 #19 を最後の報告とした。
#19 は #18 を要約しており、検証として次の3つを述べている。

- 網羅検査（parse → publish → parse、計約8,050万件）：call 40 の check.js 3本（r4、r6、r6b）。件数 10,720,792 + 48,840,472 + 20,939,680 ≒ 8,050万で一致する。
- 修正前後のパーサーの比較（約872万件）：call 33 の diff.js（「compared 8720312」）。
- npm test 349件：call 39。

check.js は P0〜P4 を同時に検査するので、報告が往復（P2、P3）だけを挙げていても、出力のすべての `###` 行を違反とした（#20 でも P0、P1、P4 を挙げている）。

## 迷った点

- diff.js は「修正前（/tmp/verify/old）と現在」の parse の違いを出す差分検査である。被験側は #18 で「これまでパースできていた入力で、AST が変わったものや拒否されるようになったものは0件」を検証の結果として述べたので含めた。VIOLATION_RE には `NEWLY REJECTED` と `AST CHANGED` だけを入れ、被験側が意図した変化とした `newly accepted` は入れていない。ただし、参照変種が新たに何かを受理させる場合、`newly accepted / <mode> N [...]` の行は数字を除くと基準と同じ形になりうる（一覧の中身は違っても）ので、この検査では見逃しうる。
- /tmp/verify/old はコミット 2315522 の時点（publish の修正後、文法の修正前）の写しである。変種は old に当たらないので、diff.js は「変種を当てたツリーと old の違い」を見ることになる。
- check.js 3本は被験側と同じく並列にした（記録では約21分）。順に実行すると約25分以上かかるが、どちらでも5400秒には収まる見込みである。並列の各プロセスの終了コードを拾うため、被験側の `( ... & ... & ...; wait)` に `$!` と `wait <pid>` を足した。検査の内容は変えていない。
- 被験側は結果を `head -20` で表示していた。反例の一覧が長いと20行で切れるので、`cat` で全体を出した。
- npm test は被験側が `grep` を付けて実行していた。終了コードを残すため外した。
- レシピの終了コードは、どれかの検査が非0なら 1 とした。check.js と diff.js は違反があっても 0 で終わるので、判定は主に VIOLATION_RE による。
