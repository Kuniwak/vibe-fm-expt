## 迷った点

- Lean の検査は JS のコードを読まない（手で書き写したモデルの定理）。依頼文に従い、`lake build` が通るかを見る手順として含めた。参照変種はこの検査には現れないはずである。
- `lake env lean /tmp/Check.lean`（公理の確認）は、報告で「使っている公理は…だけ」と述べているので含めた。同じ call 22 の `grep -rn "sorry\|admit\|axiom"` は、該当なしで終了コード 1 を返すので含めず、`sorryAx` を VIOLATION_RE に入れて代えた。
- npm test は被験側が `npm test 2>&1 | tail -8` で実行していた（call 24、約8秒）。`tail` を付けると終了コードが失われるので外した。出力に `passing` の行が出ていない（tail -8 がカバレッジ表と typecheck の部分だけを拾った）ため、記録からは件数を確かめられない。被験側は「既存のテストもすべて通っています」と述べている。
- レシピの終了コードは、各検査のどれかが非0なら 1 とした。fuzz.js、rt.js、cov.js は違反があっても終了コード 0 なので、判定は主に VIOLATION_RE による。
- cov.js は `lib/traversing.js` のソースを正規表現 `^  ([A-Z_]+): \{` で読んで `_childNodesMap` のキーを数える。変種が書式を変えると「missing in _childNodesMap」が出ることがある（それも違反の行として数える）。

## 入力について

- 違反として具体的に挙げたのは、手で組み立てた AST `OPTIONAL(UNION(A,B))` の出力 `A | B=` だけである。型式の入力ではなく AST なので、出力された文字列を input 列に書き、note に AST を書いた。被験側自身は #14 で「仕様の制約」と扱っており、違反と見るかは判断が分かれる。
- call 5 の fuzz.js の不一致（`""`、`"\\"` など 111974 件）は、`JSON.stringify` のキー順による比較の誤りで、被験側は #3 で撤回し、call 7 で 0 件になった。違反として含めていない。
