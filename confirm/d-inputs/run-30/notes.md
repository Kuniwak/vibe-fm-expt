## 迷った点
- **S3 に `timeout 900` を付けるか。** 段階3で被験側が check.js を実行したのは call 25 だけで、そこでは `timeout 900` が付いている（#13「各実行には15分のタイムアウト」）。S3 は段階3の時点の写しなので、これを写した。S1 は call 17 のとおり、timeout なしにした。check.js は止まらないとき何も出力しないので、どちらのレシピでも結果は exit 124 になる。違いはかかる時間だけ。ただし、変種で検査が遅くなると 900 秒を超えて exit 124 になるおそれがある。実際、被験側の m3b は並列実行で 815 秒かかった。
- **npm test を含めるか。** 含めなかった。#4 は既存のテストを検証と分けて述べており、#13 が検証と呼んでいるのも check.js だけ。被験側は段階1で回帰テストを6件足しているが、それは修正したバグ2件の固定であり、報告では検証として扱っていない。ハーネス側が含める場合のコマンドの原文は `npm test`（call 17）。
- **VIOLATION_RE の取り方。** check.js は常に exit 0 で、出力は util.inspect の形。性質のキーの行（`'P1 ...': [`）に加えて、入力の行（`s: '...'`）も当てた。orig モードでは、基準の出力に P1/P2 のキーがもう出ているはずだからである（固定時点のライブラリには #4 の2件がある）。数字を除いて比べるので、`?1?` と `?-1?` は同じ形になる。表示は性質ごとに先頭の15件まで。
- **inputs の範囲。** S1 には `/tmp/verify/all.txt`（call 7 の出力。写しに残っている）の全入力を入れた。#4 で被験側が挙げた `?a?`、`!a?`、`?a!`、`??!`、`typeof b.c` はこれに含まれる。all.txt は permissive/TopTypeExpr だけを集めたもの。修正の前の木での違反で、#6 で直っている。kind は、段階1では種類が渡されていないので `—` にした。
- S3-timeout にはこれに加えて `...a|b`（kind 1）を入れた。#13 で被験側が、変種なしの状態での表との食い違いとして挙げたもの。check.js の出力ではなく、手で表と照合して見つけている（call 21、27）。
- `?a|b`、`a|...b`、`{}`、`{a}`、`{"s"}`、`{1}`、`?{}`、`...{}`、`0x1`、`.5`、`+1`、`0b1`、`b.cb.c`、`b.c`、`?a` は、被験側の変種でだけ出た違反なので入れなかった。なお `a|...b` は、元の木では正しく拒否されると被験側が述べている。
