## レシピについて迷った点

### S1：run_all.sh が写しにない
- 段階1の終わり（S1、10:59:53Z）の時点では `/tmp/verify/run_all.sh` はまだない。被験側はその約2分後（call 51、11:01:51Z）に、「いまの検証を変えずに実行する」スクリプトとして書き、ツリーは S1 と同じ状態で実行した。
- その本文は、段階1で被験側が実行したコマンド（call 5 の fuzz.js、call 25 の fuzz2.js、call 36 の cmp.js、call 48 の npm test）を並べたもの。そのため call 51 の本文をレシピに写した。
- `timeout`（600秒・300秒）は call 51 で足されたもので、段階1のコマンドにはない。外側の見張りとしてそのまま残した。
- run_all.sh はその後書き換えられ、S3 には別の版が残っている。S1 では S3 の版を使っていない。

### Lean（`cd lean && lake build`）を入れた
- #12 と #43 で、被験側は検証の一部として挙げている。
- 一方で被験側自身は、JS のコードを読まないので変種の影響を受けないとして、run_all.sh から外した（#22）。
- 入れても判定には効かない見込みだが、報告で検証として述べたものなので両方のレシピの最後に入れた。外すかどうかはハーネス側で決められる。

### S3：`npm run verify` と run_all.sh のどちらにするか
- #36 は「`npm run verify` で実行できます」と書いている。これは `node verification/check.js` を `--baseline` なしで実行するもの。
- この形では、変種を入れない状態でも 12,032 件の違反で exit 1 になる。出力に出るのも各グループの先頭12件だけである。したがって、元からある違反の上に変種で新しい違反が加わっても、出力に現れないことが多い。
- 被験側が段階4で変種を確かめるときに使ったのは、`--baseline=/tmp/verify/baseline-violations.json` を付けた run_all.sh（call 120、139）と、check.js の単独実行（call 158、163、166）だった。#36 も「基準との差分」を検証の一部として挙げている。
- そこでレシピでは run_all.sh をそのまま実行した。npm test、fuzz、cmp.js、check.js（baseline 付き）がすべて含まれる。
- `npm run verify` だけを使う案に替える場合は、VIOLATION_RE をそのまま使えるが、元からある違反の例の行と区別がつかない点に注意する。

### baseline ファイル
- `/tmp/verify/baseline-violations.json` は、check.js を最後に直した後（call 152）に、call 153 で作り直されている。S3 の check.js と組になっている。
- 照合は入力、actual、detail の完全一致による。参照変種で、元からある違反の actual の木が変わった場合は「新しい違反」として出る。

### 終了コード
- どちらのレシピも最後が echo なので、終了コードでは判定できない。VIOLATION_RE（`exit=[1-9]` を含む）で判定する前提にした。

### 時間
- S1 で止まらない変種を入れた場合、外側の timeout の合計は 5400 秒を超える（600 + 5×300 + 20×300 + 600 秒）。その場合は cmp.js と lake build まで進まない。ただし、それより前に `exit=124` の行は出る。
- S3 では、変種3を入れた状態で約26分かかった（call 139）。

### MODE=orig の場合
- 被験側が足した7件の回帰テストは、元のライブラリでは失敗する（call 48）。fuzz2 も REPARSE_FAIL を出す。
- したがって、orig では基準の出力にもともと違反の行が入る。

## 入力の抜き出しについて迷った点

### 段階1の往復バグ（kind は `—`）
- 被験側はこれらを「実在するバグ」として挙げ、ライブラリを直した。どれも S1 と S3 のツリーでは直っている。
- 段階2の3種類が示される前の発見なので、被験側は分類していない。そのため kind は `—` とした。
- 「変種を当てない状態の違反」に当たる（被験側の変種によるものではない）ので、S1 と S3 の両方に含めた。
- メッセージ（#12）の5件に加えて、検査の出力（call 6 の fuzz2.js、call 7 と call 8 の min.js）で往復が失敗した入力も含めた。
- min.js は検査として残したものではなく、手で試した道具である。ただし、出力は被験側が反例として扱ったものである。

### S3 の種類1の違反
- `/tmp/verify/full_baseline.txt` にある、変種を入れない状態の 12,032 件（call 153 の出力。#42 の「12,032件」）をすべて1行ずつ入れた。入力は出力の JSON 文字列を復号したもので、`N1`、`N2` などの記号は被験側の検査が名前に当てたもので、そのまま写した。
- #36、#42 で例として挙げた入力は、すべてこの中にあった。該当する行の source にはメッセージ番号も書いた。
- call 147 の版（12,065件）は使っていない。オラクルの不具合（33件）を直す前のもので、ファイルは上書きされている。
- 段階4の途中に、オラクルを直す前の出力（call 92 の 422,327件、call 111 の `module: /` 系など）がある。これらは被験側がオラクル側の誤りとして直したもので、違反として挙げ続けたものではないので含めていない。
- #22 の手作業の照合（`?!A`、`!A?`、`A?[]`、`!A[]`、`function(): A[]`）と、#42 の補足 `B|(A)[]` も入れた。
- call 157 の `B|A<C>[]` は、メッセージには出てこない。被験側が原因 N の確認で実行した出力（拒否）にあるので入れた。迷った点である。
- `!A?` は、段階1の往復バグ（kind `—`）と、表との食い違い（kind 1）の2行になっている。

### 含めなかったもの
- 変種でだけ出た違反は含めていない。`A?|B`（変種1の往復）、`? N1 | N2`、`! 1 | 2`、`! * | *` など（変種1）、`{a}`、`{a, b: *}`（変種2）、`"a\\b"`、`"a\\"`、`"a\\"!`、`"a\\"=`（変種3）がこれに当たる。
- `?A|B`、`A|B=`、`function(): A=` も含めていない。#22 で「表どおり」とされている。
- call 34 の cmp.js の不一致（`"[]" model - js ?TUPLE` など）も含めていない。これは Lean モデル側の欠落（空タプル）で、モデルを直して0件になっている。ライブラリの違反ではない。
- Lean の Check.lean の反例（トークン列 `[q, n 0, q]` など）も含めていない。段階1のバグ1、2をモデル上で示したもので、型式の文字列としては `?A?` などと重なる。
