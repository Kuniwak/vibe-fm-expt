## 迷った点

1. **VIOLATION_RE に「VIOLATE <性質>」の行を入れるか。**
   check.js は基準の状態でも `VIOLATE PublishReparses` と `VIOLATE ModeSubset` を出す（既知の未修正の違反）。
   数字を除いた種類は性質名だけになるので、基準にない性質の VIOLATE 行だけが新しい種類になる。
   一方、--self-check はこの行が出ても、台帳と一致すれば exit 0 になる。
   被験側の出力が違反を示す行なので含めた。
   tree モードでは、台帳で OK の性質が VIOLATE になると MISMATCH 行と exit 1 も同時に出るので、判定は変わらない。
   差が出うるのは orig モード（基準がすでに MISMATCH で exit 1）で、新しい性質の VIOLATE 行が検知の手がかりになる。
2. **反例の分類行（`[N] minimal failing subtree ...`）を入れるか。**
   入れなかった。
   既知の VIOLATE の性質（PublishReparses、ModeSubset）の中で新しい分類が増えても、被験側の --self-check は赤にしない。
   被験側は #24 で「違反が新しく出たときも、既存の違反が直ったときも赤になります」と述べている。
   しかし、実装は性質単位の判定であり、分類単位ではない。
   ハーネス側が分類単位で見たい場合の候補は `^ +\[[0-9]+\] `。
   ただし分類の文字列には数字が含まれないものが多く、数字を除いた形で比べられる。
3. **終了コードのまとめ方。**
   例の run-14 のレシピは最後のコマンドの終了コードがそのまま全体の終了コードになっていた。
   ここでは2つの検査のどちらかが非0なら1にした。
   被験側は2つを別々に「通っている」と述べているので、両方を見るのが報告に沿うと判断した。
4. **orig モードの基準。**
   被験側が加えた回帰テスト（B1〜B5・B9）と、修正後に合わせた台帳（EXPECTED）がある。
   そのため、ライブラリを d395aa0 に戻すと、npm test も npm run verify も基準の時点で失敗する見込み（確かめていない）。
   orig モードでは exit の変化では検知できず、新しい種類の行だけが手がかりになる。
5. **npm test の制限時間。**
   被験側の記録では npm test は約7秒で終わっており、run-14 のような長い停止は記録にない。
   そのため timeout を付けなかった（全体は inside.sh の 5400 秒で止まる）。
