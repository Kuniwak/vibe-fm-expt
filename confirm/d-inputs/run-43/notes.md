## 迷った点

1. **S1 に /tmp/verify を含めるか。**
   段階1の最後の報告 #12 は、検証をリポジトリに組み込んだ（tests/test_properties.js）と述べている。
   一方 #9 は /tmp/verify の4本を検証スクリプトとして挙げており、段階3の #28 は「いまの検証」を test_properties.js と /tmp/verify の6本としている。
   そのため両方を含めた。/tmp/verify のコマンドは call 26 の並列実行（`&`）を、順に実行する形に直した。引数は原文と同じにした。
2. **S3 に /tmp/verify を含めるか。**
   #39 が「`/tmp/verify` は使うのをやめました」と述べているので含めなかった。
3. **npm test を含めるか。**
   どちらの写しでも、被験側が最後に実行した検査は npm test（S1 は call 33、S3 は call 96）である。報告でも npm test の結果を述べている（#12、#39）。
   そのため含めた。ただし npm test は既存の単体テストも動かすので、「被験側の検査」の範囲より広い。
   ハーネス側が被験側の性質検査だけを見たい場合は、各レシピの最初の mocha の行だけを使えばよい。
4. **timeout を足したこと。**
   S1 の検査には、入力ごとの制限時間も全体の制限時間もない。publish が無限ループする変種では、mocha も node も終わらない。
   制限時間を入れないと、最初のコマンドで全体の5400秒を使い切ってしまう。
   そこで、被験側が自分の変種に同じ検査を当てたときの値を使った。S1 は /tmp/mutants/run.sh の `timeout 600`、S3 は /tmp/mutants/run_new.sh の `timeout 1800` である。
   S3 の npm test には被験側の timeout の例がないので、1800 をそのまま使った。
5. **終了コード。**
   どれかのコマンドが非0なら、レシピは1で終わる（`rc` で集めている）。
   /tmp/verify の3本は、違反があっても0で終わる。非0になるのは、スクリプト自身が落ちたときと timeout のときだけである。
6. **VIOLATION_RE（S1）。**
   /tmp/verify の出力は JSON なので、`"prop": "P…` の行と `"s": "…"`（反例の入力）の行を対象にした。
   基準の時点でも keyof などの違反が出ている。そのため、変種で新しく現れた分類や例だけが「検知」に数えられる。
   例は分類ごとに最初の5件だけなので、既存の分類に違反が増えても、その5件に入らなければ行として現れない。
7. **orig モード。**
   S1 の test_properties.js は、修正前のライブラリでは基準の時点で失敗する（call 32「Array(280)」）。
   S3 の記録ファイルは修正後のライブラリの違反を完全一致で記録している。そのため、修正前のライブラリでも基準の時点で失敗するはずである（確かめていない）。
