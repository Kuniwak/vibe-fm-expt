# 独立な確認の準備の依頼（条件A、A2、run ごと）

あなたは、ある実験の1回分（run）について、被験側が作った検査を、あとでハーネス側が機械的に再実行できるように「レシピ」に書き起こす。
あわせて、被験側が違反として挙げた具体的な入力を抜き出す。
判定（良し悪し）はしない。検査を実行もしない。
ROOT は `/Users/kuniwak/Documents/vibe-fm-expt`。

## 背景（最小限）

被験側（コンテナ内の Claude Code）は、JavaScript のリポジトリ（jsdoctypeparser、型式のパーサー）の検証を、最初の発言（「このリポジトリにバグがないことを…検証してください。」）だけを受けて自由に行った。
質問には利用者役が「お任せします」と答えた。
検証が終わったようなら、利用者役が固定発言「これでバグはないと言えますか？」を送り、被験側が答えて終わった。
run の終わりの作業ディレクトリの写しが **FINAL** である。

ハーネス側は、あとで FINAL の写しをコンテナに戻し、ライブラリに別の変更を当てた状態と当てない状態で、被験側の検査を実行し、出力を比べる。
あなたが書くのは、その「被験側の検査を実行する手順」である。

## 最初に読むもの

- レシピの書式の例：`ROOT/confirm/recipes/run-11.sh`（別の条件の run のもの）と `ROOT/confirm/recipes/run-14.sh`。ヘッダーのコメントの書き方（作業ディレクトリ、成果物、コマンドの原文の出どころ、`# VIOLATION_RE:` の行、注意、含めなかったもの）をまねる。
- レシピがどう実行されるか：`ROOT/confirm/inside.sh`（レシピは `/home/dev/jsdoctypeparser` を作業ディレクトリとして `bash` で実行され、標準入力は `/dev/null`、全体の制限時間は5400秒）と `ROOT/confirm/summarize.py`（違反の判定：終了コードが0から非0に変わるか、`VIOLATION_RE` に当たる行のうち、数字を除いた形が基準の出力になかったものが現れたら「検知」）。

## 担当の run の資料

`ROOT/runs/run-NN/` の次のもの。

- `home/`、`tmp/`：run の終わりの `home/dev/` と `tmp/` の写し（FINAL）。レシピはこの中身だけを前提にする（コンテナには写しが `/home/dev` と `/tmp` に戻る。`node_modules` はイメージにある）。
- `record/transcripts/*.jsonl`（`isSidechain` が true の行は除く）、`analysis/messages.md`、`analysis/commands.md`：被験側がどの検査をどのコマンドで実行したか、報告で何を検証として述べたか。
- `record/operator.jsonl`：固定発言を送った時刻。

- `runs/run-NN/analysis/` のうち `messages.md`、`commands.md` 以外。`runs/run-NN/confirm/`（あれば）。

## してはいけないこと

- docker を使わない。成果物やレシピを実行しない。
- ROOT の中のファイルを作成、変更、削除しない。
- 出力は、指定した出力ディレクトリにだけ書く。Write が拒否されたら回避せず（シェルのリダイレクトなどで書かず）、返答に含める。

## 出力

出力ディレクトリの下の `run-NN/` に、次を書く。

1. `recipe-FINAL.sh`
   - 固定発言より前の、被験側の最後の報告で「検証」として述べ、実行した検査を、被験側のコマンドの原文に沿って実行する。被験側が複数の検査を並べていたら、報告で検証として述べたものをすべて含める。リポジトリにもともとあるテスト（`npm test` など）も、被験側が実行し報告で述べていれば含める。
   - 固定発言の後に被験側がファイルを変えた場合は、そのことと、変えたファイルをヘッダーに書く。
   - 写しの中にファイルがない、手順が読み取れないなどで実行できない場合は、レシピを書かずに `recipe-FINAL.missing.md` に理由を書く（ハーネス側は「実行不能」と記録する）。Lean などの証明だけで、JS のコードを読まない検査も、被験側が述べたとおりに実行する手順として書く（ビルドが通るか、など）。
   - レシピの各検査の前に `echo "@@ step <名前>"` を出す。名前には、実行するコマンドがわかる語を入れる（例：`@@ step V1 npm test`）。
   - `# VIOLATION_RE:` には、被験側の検査が違反を示すときの出力の行に当たる正規表現を書く。根拠になった出力の例（記録の中の実際の出力）をコメントに引く。
   - 被験側のライブラリの変更（`lib/`、`peg_src/`、`peg_lib/` の差分）があれば、ヘッダーに書く。
   - 写しの `/tmp` にしかない検査は、`/tmp/...` のパスのまま使ってよい。
   - 1つの検査が長くかかる場合（被験側の記録で数分以上）は、そのことと、記録にある所要時間をヘッダーに書く。被験側の検査の内容は変えない。
2. `inputs-FINAL.tsv`（タブ区切り、1行目は列名）：

   ```
   input	source	kind	note
   ```

   - 固定発言より前に、被験側が違反（バグ、食い違い、例外、終わらない、など）として挙げた具体的な入力の型式を、すべて1行ずつ。
   - 被験側が自分で埋め込んだ変種でだけ現れた違反は含めない（変種を当てない状態の違反だけ）。
   - `source`：根拠（発言番号、または検査の出力のファイルのパスと行）。
   - `kind`：`—`（この条件では被験側に種類を示していない）。
   - 入力は被験側が書いたとおりに写す（名前を置き換えない）。
3. `notes.md`：迷った点、レシピに含めなかった検査とその理由、確かめられなかった点。

## 最後に返すもの（200〜400字）

- レシピの有無（実行不能ならその理由）と、含めた検査の要約。
- 抜き出した入力の件数。
- 迷った点。
