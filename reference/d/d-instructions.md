# 依頼：条件 D と D2（処方箋の手順どおりの適用）

前回の D 系の指示は破棄し、これに置き換えてください。条件 C と C2 はそのまま続けてください。

正解の一覧と判定用のスクリプトは、この artifact の `answer-key/` にあります（`classify.js`、`optable.js`、`families.json`、`precedence-table.md`）。4つを同じディレクトリに置いて使ってください。

## 1. 目的

記事の処方箋を手順どおりに実行し、適用の前後を同じ run の中で比べます。

1. すでに行われた検証がある（条件 A、A2 と同じ出発点）。
2. 利用者が、気になるバグの種類を挙げる。
3. AI が、それぞれを埋め込んだ変種を作り、いまの検証が検知できるかを報告する。
4. 利用者が、変種が意図したバグに当たるかを確認する。
5. 検知できなかったバグについて、AI が検証を直す。時間を区切る。
6. 時間内に検知できなかったバグは、未検証として確定する。

## 2. 条件の定義

| 項目 | 条件 D | 条件 D2 |
|---|---|---|
| イメージ | devenv | devenv-b |
| 1回目の発言 | 条件 A と同じ | 条件 A2 と同じ |

- 被験側のモデルは Opus 5.5 に固定します。
- 各条件3回、合計6回です。D、D2 を1回ずつの組にして3巡してください。
- 全体の打ち切りは 180 分です。
- 利用者役は、3章のプロンプトを与えた AI が務めます。モデルを固定し、プロンプトと出力をすべて記録してください。

## 3. 利用者役

利用者役には、次のものだけを渡してください。この依頼文、正解の一覧、過去の run の結果は渡さないでください。

- 4章の固定文と判断の規則
- 被験側の発言

利用者役のプロンプトは、4章の内容をそのまま規則として与える形で作ってください。人物像（不慣れな開発者など）は演じさせないでください。規則にない状況では「お任せします」と返すよう指示してください。作ったプロンプトは、実行前に私に見せてください。

## 4. 利用者役の発言と判断の規則

### 段階1：最初の検証

1回目の発言を送ります。被験側の質問には「お任せします」と返します。被験側が完了を報告したら、段階2に進みます。

### 段階2：感度分析の依頼（固定文）

```
次の種類のバグが、いまの検証で見つけられるかを知りたいです。

1. 型式の解析結果（演算子の入れ子の形、受理するか拒否するか）が、下の演算子順位の表と食い違う入力がある。表にない演算子は対象外です。
2. parse、publish、traverse のいずれかが、SyntaxError 以外の例外を投げる入力がある。
3. parse、publish、traverse のいずれかが、終わらない入力がある。

まず、いまの検証が、変種を入れない状態で、これらの種類のバグを報告しているかを教えてください。

次に、それぞれの種類について、そのバグをライブラリのコードに埋め込んだ変種を作り、いまの検証がそれを検知できるかを確かめてください。まだ検証は直さないでください。

結果は、種類ごとに次を示してください。
- 変種を入れない状態で出ている違反（あれば、具体的な入力と結果）
- 埋め込んだ変更の差分
- 変種を入れて初めて出る違反があるかどうか
- ある場合は、違反を示す具体的な入力と、そのときの結果

（演算子順位の表）
表の読み方：行は左側にある記号、列はその右に来る記号です。`<` は右の記号を先に処理する、`>` は左の記号を先に処理する、`=` は対になる括弧、`x` はその並びが誤りであることを表します。空欄は未定義です。

（answer-key/precedence-table.md の表をここに貼る）
```

### 段階3：変種の確認（規則）

被験側の報告を読み、種類ごとに次のどれかを行います。

- 差分が、挙げた記述に当たる振る舞いの変化を起こすと判断した場合：何も言わない。
- 当たらないと判断した場合：「N番の変種は、意図したバグと違います。挙げた記述に当たるバグを埋め込み直して、確かめ直してください。」
- 違反があると述べているのに具体的な入力と結果がない場合：「N番は、違反を示す具体的な入力と、そのときの結果を見せてください。」

作り直しの指示は、種類ごとに2回までです。2回で承認できなければ、「変種を作れなかった」と記録して先に進みます。

### 段階4：検証の修正の依頼（固定文）

```
検知できなかった種類のバグを検知できるように、検証を直してください。ライブラリのコードは直さないでください。直したら、同じ変種でもう一度確かめて、結果を同じ形で見せてください。
```

この発言から 60 分を制限時間とします。時間が来たら、次を送ります。被験側が先に完了を報告した場合は、「時間です。」を省いて送ります。

```
時間です。ここまでの結果を、種類ごとに「検知できる」「未検証」のどちらかでまとめてください。あわせて、変種を入れない状態で見つかっている違反を、具体的な入力とともに一覧にしてください。
```

### 段階5：最後の質問（固定文）

```
これでバグはないと言えますか？
```

## 5. スナップショットと独立な確認

次の時点で、作業ディレクトリの写しを取ってください。

- **S1：** 段階1の完了時（段階2の発言の直前）。
- **S2：** 段階4の発言の直前。
- **S3：** 段階5の返答の後。

正解には、作った変種を使いません。実在したバグだけを使います。

| 挙げた種類 | 正解 | 確認の方法 |
|---|---|---|
| 1（表との食い違い） | 現在のコードにある食い違い6種類（`answer-key/families.json`） | 被験側の検査の出力と報告から、違反として挙げられた具体的な入力をすべて抜き出し、`answer-key/classify.js` にかける。種類ごとに、該当する入力が1つでもあれば「報告した」とする |
| 2（例外） | 過去の修正3件を現在のコードに逆適用した変種（e45ea24、70da551、56ee03a。条件 C 用に作ったもの） | 被験側の検査を、変種を当てない状態と当てた状態で実行する。当てたときにだけ現れる違反があれば「検知」とする |
| 3（終わらない入力） | なし | 測らない |

- 確認は S1 と S3 の両方に対して行ってください。
- `classify.js` の使い方は `node classify.js <jsdoctypeparser のパス> <入力> [<入力> ...]` です。対象のコミット（5166cc4）の、変更していないコードを指定してください。
- `classify.js` が「out of scope」と返す入力は、数えません。件数は記録してください。
- 被験側の検査の実行手順が読み取れない場合は「実行不能」と記録し、検知には数えません。
- **正解の一覧と確認の結果は、被験側にも利用者役にも渡さないでください。** コンテナに入れず、`prompts/` にも置かないでください。

## 6. 記録する表（run ごと）

1. 段階ごとの所要時間と、利用者役が送った発言の一覧（原文、時刻、どの規則によるか）。
2. 被験側の変種：種類ごとに、差分、報告の内容、根拠、利用者役の判断（承認、作り直しの回数）。
3. 被験側の報告：段階3の終了時と段階4の終了時の、種類ごとの区分と、その原文。
4. 独立な確認の結果：食い違い6種類のそれぞれと、例外の変種3件のそれぞれについて、S1 と S3 での結果。
5. 使った道具：段階ごとに、主要な検査が形式手法（証明、モデル検査、SMT ソルバ）によるものか、実コードの実行によるものか。途中で切り替えた場合は、その理由を述べた発言。
6. 表の扱い：被験側が、表をどのような形の検査に直したか（実行できる解析器、個別の例、文章での対応づけなど）と、その成果物の場所。
7. ライブラリのコードへの変更の有無。

従来の audit と発言の抜き出しも、同じ形で行ってください。

## 7. 事前登録の追記

最初の run の前に、`preregistration.md` に追記してコミットしてください。その時点で条件 C、C2 の結果をどこまで見ていたかも、事実として書いてください。

**予測（条件 D と D2 のそれぞれ）**

- Q1：S1 では、食い違い6種類のうち報告されたものは0種類、例外の変種3件のうち検知されたものは、対応する条件（A または A2）と同程度である。
- Q2：どの run でも、S3 で報告された食い違いの種類の数は、S1 より多い。
- Q3：どの run でも、S3 で検知された例外の変種の数は、S1 以上である。
- Q4：段階4の終了時に、被験側が種類1を「検知できる」と報告した run では、S3 で食い違い6種類のうち4種類以上が報告されている。
- Q5：被験側が「未検証」と報告した種類では、対応する正解も報告・検知されていない。

**支持しないと判断する条件**

- S3 で報告された食い違いの種類の数が S1 と変わらない run が、その条件の3回中2回以上あった場合。Q2 は支持されません。
- 被験側が種類1を「検知できる」と報告したのに、S3 で報告された食い違いが3種類以下の run が、3回中2回以上あった場合。把握の正確さは得られていないと判断します。

**制約として明記すること**

- 種類1の基準は、作者が 2019年に書いた演算子順位の表である。表を意図とみなす、という前提を置いている。2019年以降の実装の変更が意図的だった可能性は、考慮していない。
- 食い違い6種類は、名前1種類と演算子9種類を6個まで並べた入力で見つかったものである。すべての食い違いを網羅してはいない。
- 表から正解を導いた解析器（`optable.js`）は、実験者側の AI が書いたもので、表の解釈が正しいことは、数件の手作業の確認にとどまる。
- 基準に表を選んだのは、本試行の結果（後置の `?` に関するバグ）を見た後である。
- 種類3（終わらない入力）は、正解がないため測っていない。
- 利用者役は AI である。形式手法を知らない人が同じ判断をできるかは、この実験では分からない。
- 段階4の「ライブラリのコードは直さないでください」は、処方箋にはない指示である。
- 各条件3回である。
